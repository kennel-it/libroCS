API

Application programming interface

Con il termine API si possono indicare due cose: delle librerie da usare in un qualche linguaggio di programmazione o dei servizi disponibili via web. Entrambe sono un contratto che specifica cosa chiedere e come, la prima ci consente di chiedere di fare qualcosa ad un pezzo di codice che verrà eseguito nel nostro programma e la seconda di usare un servizio disponibile in rete. Qui ci occuperemo della seconda.

Perché: usiamo delle API web quando la nostra applicazione non può fare tutto da sola. Può avere bisogno di informazioni che possiede qualcun altro e che sarebbe impossibile o troppo costoso raccogliere in proprio (ad esempio le previsioni meteo, che richiedono una rete di stazioni di misura), oppure di agire sui sistemi di qualcun altro (ad esempio pagare un ordine, pubblicare un contenuto, registrare un'informazione). In entrambi i casi l'altro sistema è già in funzione, scritto da altri e con tecnologie che non scegliamo noi: l'API web è lo strumento con cui quel sistema ci permette di usarlo senza conoscerne l’interno.

Come: esistono molti modi con cui un'applicazione può chiedere qualcosa a un'altra attraverso la rete, e ciascuno ha le sue regole su come formulare la richiesta e come ricevere la risposta. Noi ci concentreremo su REpresentational State Transfer (solitamente scritto con l'acronimo REST), per due motivi. Il primo è che si appoggia su ciò che già conosciamo: usa HTTP per comunicare e di solito risponde in JSON, quindi non richiede strumenti nuovi. Il secondo è che oggi è largamente lo stile più diffuso: la grande maggioranza delle API che incontrerete, dai servizi pubblici come quelli di GitHub o Google alle applicazioni aziendali, è di questo tipo, e ciò che si impara qui serve ovunque.

REST

Questo tipo di architettura si presta molto bene all'uso in sistemi client/server orientati ai servizi come quelli WEB e ha le seguenti caratteristiche:

  • usa HTTP come protocollo per trasferire i dati
  • non usa le sessioni: ogni richiesta viene elaborata senza tener conto delle richieste precedenti perché porta con sé tutto ciò che serve (autenticazione compresa), quindi il server non ricorda nulla e volendo si può replicare facilmente
  • gli oggetti vengono indicati tramite URL (es: https://api.magazzino.com/fornitori/138)
  • le azioni da compiere sull'oggetto sono quelle di HTTP

Vediamo un esempio pratico: un sistema per organizzare gare di corsa. Nella tabella ogni riga è una richiesta al server: l'azione è il metodo HTTP e il path indica l'oggetto su cui agire (è la parte della URL che segue il dominio, ad esempio https://api.gare.example/gare/42 ha path /gare/42).

AzionePathSpiegazione
GET/gareelenco delle gare
GET/gare/42informazioni dettagliate della gara 42
GET/gare/42/iscrizionielenco degli iscritti alla gara 42
GET/gare/42/iscrizioni?categoria=juniorsolo gli iscritti di una categoria (ricerca via parametri)
POST/gare/42/iscrizioniiscrive un nuovo partecipante (i dati stanno nel corpo della richiesta)
GET/gare/42/iscrizioni/7dati dell'iscrizione 7
PUT/gare/42/iscrizioni/7sostituisce i dati dell'iscrizione 7
PATCH/gare/42/iscrizioni/7modifica solo alcuni campi (es. la taglia della maglia)
DELETE/gare/42/iscrizioni/7annulla l'iscrizione 7

Quelle qui sopra sono richieste, non è detto che il server accetti di fare quello che viene chiesto. Una volta inviata la richiesta bisogna aspettare di vederne l'esito nella risposta: non tutti i server si comportano in maniera ortodossa usando il codice HTTP (ad esempio 201 CREATED dopo un POST), a volte la risposta è sempre 200 e poi nel corpo c'è una descrizione dell'esito, questo comportamento purtroppo varia da server a server.

Altri aspetti comodi di questo tipo di API sono anche:

  • i parametri (in particolare per le ricerche) sono forniti utilizzando il solito sistema del GET di HTTP
  • normalmente la risposta può essere fornita in più formati ma JSON è quello più usato
  • per fare i primi test è sufficiente usare un browser oppure programmi dedicati come Bruno o Postman che però richiede di registrarsi.

Moltissimi servizi on-line permettono di interfacciarsi usando delle API pubbliche che molto spesso sono REST in qualche misura (nel senso che potrebbero non rispettarne tutti i vincoli), l'unico inconveniente è che per poterle usare è necessario usare delle chiavi di accesso che vengono concesse ad ogni utente (oppure alle singole applicazioni che si vogliono creare) previa registrazione; questo vale per Facebook, Instagram, Google e tantissimi altri.

Un esempio: l'API di GitHub

GitHub permette l'accesso (limitando il numero di richieste al minuto) anche senza registrazione utilizzando una API REST, questo ci permette di fare alcuni esperimenti semplicemente scrivendo una URL nella barra degli indirizzi del browser.

Come primo esperimento possiamo provare a fare una ricerca per trovare un progetto su GitHub, per farlo seguiamo le indicazioni Search repositories e visto che vogliamo cercare un progetto sui questionari scritto in php usiamo la URL https://api.github.com/search/repositories?q=questionario+language:php e inviamo una richiesta GET al server che come risposta ci fornisce un oggetto JSON che elenca tanti progetti (la risposta non viene riportata qui per intero perché è lunga 170kB, quella qui sotto è stata pesantemente scorciata senza però semplificarne la struttura).
